# 체험마을 AI사무장 - 배포 런북 (Deployment & Operations Runbook)

## 0. 문서 목적

배포, 장애 발생, 일상적인 점검 상황에서 "무엇을 순서대로 확인해야 하는가"를 미리 정리해, 혼자 개발하는 상황에서 문제가 생겼을 때 당황하지 않고 체계적으로 대응할 수 있도록 하는 운영 매뉴얼이다.

---

## 1. 최초 배포 절차 (Cold Start)

### 1-1. 사전 준비 확인

- [ ] pyproject.toml, uv.lock, .python-version이 저장소에 포함되어 있는가
- [ ] .env가 .gitignore에 포함되어 있어 커밋되지 않았는가
- [ ] .env.example에 필요한 모든 키 이름이 빠짐없이 나열되어 있는가
- [ ] 계정·API키 관리대장(별도 문서)에서 모든 키 발급이 완료되었는가

### 1-2. Vercel 프로젝트 생성 및 연결

1. Vercel 대시보드에서 New Project 선택
2. GitHub 저장소(chonmuseojang) 연결
3. Framework Preset은 자동 감지되지 않으면 Other로 설정하고, FastAPI 진입점(api/index.py)이 인식되는지 확인
4. Environment Variables 메뉴에서 계정·API키 관리대장의 모든 환경변수를 등록(Production, Preview, Development 환경 모두 등록 여부 결정)
5. Deploy 클릭

### 1-3. 최초 배포 후 확인

- [ ] 배포된 URL로 접속 시 홈 화면(/)이 정상 표시되는가
- [ ] /api/villages 호출 시 빈 배열이라도 오류 없이 JSON이 반환되는가(아직 동기화 전이므로 빈 배열은 정상)
- [ ] Vercel 함수 로그에 에러가 없는가

### 1-4. Supabase 연결 확인

1. Supabase 대시보드에서 SQL Editor를 열고 TRD 8장의 테이블 생성 스크립트(villages_cache, **operators**, bookings, reviews, **contents**, sync_logs)를 실행
2. Table Editor에서 테이블이 정상 생성되었는지 확인
3. 배포된 서비스에서 데이터베이스 연결 테스트(간단한 조회 API 호출)

### 1-5. 최초 공공데이터 동기화 실행

1. /api/cron/sync 엔드포인트를 CRON_SECRET 헤더와 함께 수동 호출(Postman 또는 curl 사용)
2. sync_logs 테이블에 실행 기록이 남았는지 확인
3. villages_cache 테이블에 광주·전남 마을 데이터가 채워졌는지 확인
4. 데이터 딕셔너리 문서의 2장(실제 API 응답 필드 매핑표)을 이 시점에 실제 값으로 채워넣는다

---

## 2. 일상적인 배포 절차 (기능 추가 시)

1. 로컬에서 uv run uvicorn main:app --reload로 정상 동작 확인
2. uv run pytest로 전체 테스트 통과 확인
3. Git 커밋 시 pyproject.toml과 uv.lock이 최신 상태인지 확인(패키지 추가한 경우)
4. GitHub에 푸시
5. Vercel이 자동으로 감지하여 새 배포(Deployment)를 생성
6. Vercel 대시보드에서 배포 상태가 Ready로 바뀔 때까지 대기
7. 배포된 URL에서 변경한 기능이 실제로 반영되었는지 확인

---

## 3. Vercel Cron 설정 확인 절차

1. vercel.json에 crons 설정이 포함된 상태로 배포되었는지 확인
2. Vercel 대시보드의 프로젝트 설정 > Cron Jobs 메뉴에서 등록된 스케줄이 보이는지 확인
3. 설정한 시각 이후 sync_logs 테이블에 자동 실행 기록이 추가되는지 다음날 확인
4. Vercel 무료 플랜의 Cron 실행 관련 제한사항(호출 빈도 등)이 있는지 최신 정책을 배포 전 재확인

---

## 4. 장애 대응 절차

### 4-1. 웹 화면이 전혀 뜨지 않을 때

1. Vercel 대시보드에서 최근 배포가 실패(Failed) 상태인지 확인
2. 실패했다면 빌드 로그에서 오류 메시지 확인(대부분 의존성 설치 실패 또는 문법 오류)
3. 로컬에서 동일한 커밋으로 uv run uvicorn main:app --reload가 정상 동작하는지 재현 시도
4. 재현되면 로컬에서 수정 후 다시 푸시, 재현되지 않으면 Vercel 환경변수 누락 여부 확인

### 4-2. 공공데이터가 갱신되지 않을 때

1. sync_logs 테이블에서 최근 실행 기록의 status가 failure인지 확인
2. message 필드의 오류 내용 확인(대부분 서비스키 만료 또는 API 서버 응답 지연)
3. 공공데이터포털에서 서비스키 상태(활용신청 만료 여부) 확인
4. 임시 조치로 이전 캐싱 데이터가 유지되고 있는지 확인(서비스 자체는 중단되지 않아야 함)
5. 문제 해결 후 /api/cron/sync를 수동으로 재호출하여 즉시 재동기화

### 4-3. 카카오톡 챗봇이 응답하지 않을 때 (이번 카카오 연동)

1. 카카오 i 오픈빌더 관리자센터에서 스킬 URL이 올바르게 등록되어 있는지 확인
2. Vercel 함수 로그에서 해당 요청이 실제로 수신되었는지 확인(수신 자체가 안 되면 URL 문제, 수신은 됐는데 응답이 이상하면 응답 포맷 문제)
3. 5초 응답 시간을 초과하지 않았는지 로그의 처리 시간 확인
4. 카카오 스킬 응답 규격(version, template.outputs)이 정확히 지켜졌는지 재검토

### 4-4. LLM 응답이 이상하거나 실패할 때

1. 현재 LLM_PROVIDER 환경변수 값 확인
2. 해당 LLM 제공자의 서비스 상태 페이지(장애 공지 등) 확인
3. 임시로 LLM_PROVIDER 값을 다른 제공자로 변경하여 재배포, 정상 작동 여부 확인(멀티 LLM 설계의 실질적 활용)
4. API 키 사용량 한도 초과 여부 확인(대시보드에서 사용량 확인)

### 4-5. Supabase 프로젝트가 휴면(Pause) 상태가 되었을 때

1. Supabase 대시보드에서 프로젝트 상태 확인
2. 휴면 상태라면 Resume 버튼 클릭(재활성화까지 약 30초~1분 소요)
3. 재발 방지를 위해 공공데이터 동기화 크론이 정상적으로 매일 실행되고 있는지 재확인(정기 접근이 휴면 방지 효과 겸함)

---

## 5. 정기 점검 체크리스트 (주 1회 권장)

- [ ] Vercel 대시보드에서 최근 함수 오류 로그 확인
- [ ] sync_logs 테이블에서 최근 7일간 동기화 실패 이력이 있는지 확인
- [ ] 각 LLM 제공자의 API 사용량 및 비용이 예산 범위 내인지 확인
- [ ] Supabase 프로젝트가 휴면 상태가 아닌지 확인
- [ ] bookings 테이블에서 pending 상태로 오래 남은 예약이 있는지 확인. 이번 단계는 운영자가 `예약 현황`으로 봤는지 본다. 선톡 점검은 단계 성공 후 다음 단계다

---

## 6. 발표(중간/최종/시연) 전 최종 점검 체크리스트

- [ ] 배포된 URL이 정상 접속되는지 발표 당일 아침 재확인
- [ ] 시연할 질의 시나리오(예: "아이와 갈만한 갯벌체험") 3~5개를 미리 테스트해 정상 응답 확인
- [ ] 지도 화면에 마을 마커가 정상 표시되는지 확인
- [ ] 인터넷 연결이 불안정할 경우를 대비해 화면 녹화본 또는 스크린샷을 백업으로 준비
- [ ] LLM API 사용량이 한도에 근접하지 않았는지 사전 확인(발표 중 한도 초과로 응답 실패 방지)
