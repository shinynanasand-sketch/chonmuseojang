## 1. 개요 (Introduction)

### 1-1. 목적

이 문서는 "체험마을 AI사무장" 소프트웨어가 만족해야 할 기능적·비기능적 요구사항을 명확히 정의한다. PRD가 "무엇을, 왜 만드는가"를 다루고 TRD가 "어떻게 구현하는가"를 다룬다면, 본 SRD는 그 사이에서 "요구사항이 정확히 무엇이며 어떻게 검증할 것인가"를 규정하는 역할을 한다.

### 1-2. 범위

본 소프트웨어는 다음을 포함한다.

- 광주·전남 지역 농촌체험마을 정보를 제공하는 웹 기반 대시보드(1차 구현 대상)
- 하나의 카카오톡 채널·챗봇으로 운영자(사무장)와 일반 사용자(관광객)를 모두 처리하는 기능(2차 구현 대상)
- 카카오톡 Phase A 시나리오 3개와 블록 6개. `관광객_마을정보`(마을 추천, 후기 조회), `운영자_예약관리`(예약 현황 조회, 예약승인, 예약거절), `운영자_등록`(운영자 등록). 목록 성공과 한 문장 결과·안내는 `simpleText`다. 예약 접수, 후기 등록도 포함한다(2차 구현 대상)
- 공공데이터(농촌체험마을 표준데이터) 및 한국관광공사 TourAPI를 활용한 정보 제공
- 여러 LLM(대형언어모델) 중 하나를 선택적으로 활용하는 AI 추천 및 콘텐츠 생성 기능

본 소프트웨어는 다음을 포함하지 않는다.

- 광주·전남 외 지역의 농촌체험마을 정보 제공 (향후 확장 검토 대상이며 현재 범위 아님)
- 실제 결제(비용 정산) 처리 기능
- 사업자등록증이 필요한 정식 알림톡, 비즈니스 인증 채널 기능
- 이번 단계의 비즈월렛 및 카카오 이벤트 API 선제 알림(푸시). 이번 단계가 완료되고 성공한 다음 단계에서 구현한다
- 멀티턴 대화와 가변 품목 파싱은 Phase B로 보류됨. 탈출 블록도 그때 다룬다. 웰컴 블록은 서비스 소개와 사용 예시, 폴백 블록은 Phase A 블록을 떠올릴 수 있는 안내로 이미 교체했다

### 1-3. 용어 정의

| 용어 | 정의 |
|---|---|
| 대표자 | 농촌체험마을의 공공데이터상 등록된 운영주체(이장, 운영협의회 등 포함) |
| 신뢰도 점수 | 마을 정보의 신뢰 가능성을 수치화한 지표로, 등급·최신성·후기를 종합해 산출 |
| 스킬 API | 카카오 i 오픈빌더가 외부 서버와 통신하기 위해 사용하는 Webhook 방식의 REST API |
| 이벤트 API | 카카오 챗봇이 사용자에게 먼저 메시지를 보낼 때 쓰는 유료 API. 비즈월렛이 필요하다. 이번 단계에서는 호출하지 않고, 이번 단계가 완료되고 성공한 다음 단계에서 구현한다 |
| 관광객 모드 | `userRequest.user.id`가 `operators`에 없을 때의 카카오 응답. 추천·예약 신청·후기·발화 `내 예약`(본인 `customer_kakao_id` 예약만)이 가능하다. 예약 상태를 바꿀 수 없고, 발화 `예약 현황`은 운영자 기능이라 등록 안내만 한다 |
| 운영자 모드 | `userRequest.user.id`가 `operators.kakao_user_id`와 일치할 때의 카카오 응답. `role=village`는 예약 현황·승인·거절·홍보·체험 달력 등록을 한다. `role=program`은 자기 체험 글만 고치고, 같은 마을 글과 자기 체험 달력·예약은 읽기만 한다 |
| 캐시(Cache) | 공공데이터 OpenAPI로부터 주기적으로 가져와 Supabase에 저장해 둔 사본 데이터 |
| LLM 제공자 | Gemini, Claude, GPT 등 실제 텍스트 생성을 수행하는 외부 인공지능 서비스 |
| 마을 운영자 | `operators.role=village`. 마을당 1명. 예약·후기·공개 홍보·체험 달력을 다룬다. 달력에서 그 날짜의 예약을 예약번호와 대기로 보고 승인·거절한다. 체험 글은 읽기만 한다 |
| 체험 담당 | `operators.role=program`. 한 체험(`program_key`)당 1명. 자기 체험 글만 고친다. 자기 체험 달력과 예약만 읽는다. 예약 승인·거절, 홍보, 달력 등록·삭제는 하지 못한다 |
| 멀티테넌시(데이터 격리) | 운영 데이터는 `village_id`로 마을을 나누고, 체험 글 쓰기는 `program_key`로 다시 나눈다. 다른 마을 데이터는 읽지도 고치지도 못한다 |
| 현재 운영자 마을 | 인증된 운영자 세션 또는 카카오 식별자로 식별된 운영자가 접근 권한을 갖는 `village_id`. 서버 로직에서는 `current_operator.village_id`로 표기한다 |

### 1-4. 참고 문서

- 체험마을 AI사무장 제안서(기획서) — 문제정의, 목표, 기대효과
- 체험마을 AI사무장 PRD — 기능 목록, 화면 구성, 사용자 시나리오
- 체험마을 AI사무장 TRD — 시스템 아키텍처, API 명세, DB 스키마, 배포 방식

### 1-5. 문서 구성

본 문서는 전체 시스템 개요(2장), 세부 요구사항(3장, 기능/비기능/데이터/인터페이스), 요구사항 추적표(4장), 검증 기준(5장) 순으로 구성된다.

## 2. 전체 설명 (Overall Description)

### 2-1. 제품 관점

체험마을 AI사무장은 독립형 웹 애플리케이션이며, 동시에 카카오톡이라는 외부 플랫폼과 연동되는 하이브리드 서비스다. 기존에 존재하는 공공 농촌관광 포털(웰촌, jnfarmtour 등)을 대체하는 것이 아니라, 그 정보의 생산·갱신 주체(운영자)의 부담을 낮추는 보완적 역할을 수행한다.

### 2-2. 제품 기능 요약

| 구분 | 기능 |
|---|---|
| 정보 제공 | 자연어 기반 마을 추천, 지도 시각화, 주변 관광정보 제공 |
| 운영 지원 | 예약 접수·조회·승인/거절, 후기 수집, 운영 현황 대시보드, 신뢰도 점수 산정, **운영자별 데이터 격리(자기 마을만 접근)** |
| 카카오 채널 | 채널·챗봇 1개로 관광객/운영자 자동 분기, 운영자 자가 등록. 예약 알림은 푸시가 아니라 조회 |
| 콘텐츠 지원 | 운영자가 제공한 간단한 정보를 홍보문구·소개글로 자동 확장 생성 |
| 데이터 관리 | 공공데이터 실시간 동기화, 광주·전남 지역 필터링 |

### 2-3. 사용자 특성

| 사용자 유형 | 특성 |
|---|---|
| 관광객(일반 사용자) | 일반적인 스마트폰·PC 사용자, 카카오톡과 웹 브라우저 사용에 익숙함. 운영자와 같은 카카오톡 채널을 쓴다 |
| 운영자(사무장) | 고령층 비중이 높고 디지털 기기 사용에 익숙하지 않을 수 있음, 카카오톡 메시지·사진 전송 수준의 조작만 가능하다고 가정. 같은 채널에서 발화 `예약 현황`으로 자기 마을 예약을 확인한다 |
| 관리자(개발자 본인) | 시스템 운영·모니터링을 담당, 기술적 배경 지식은 제한적이나 Cursor의 지원을 받아 유지보수 |

### 2-4. 제약사항

- 개발 인력은 1인이며, 주 3일, 1일 1~2시간의 매우 제한된 개발 시간 내에서 구현되어야 한다
- 개발자는 비전문가로, Cursor(AI 페어 프로그래밍 도구)의 지원을 전제로 구현 가능한 수준의 복잡도를 유지해야 한다
- 배포 환경은 서버리스(Vercel) 특성상 상태를 서버 내부에 저장할 수 없으며, 모든 영속 데이터는 외부 데이터베이스(Supabase)에 저장해야 한다
- 카카오톡 관련 기능 중 사업자등록증이 필요한 기능(정식 알림톡, 비즈니스 인증)은 사용할 수 없다. 이번 단계의 예약 안내는 운영자 또는 관광객이 챗봇에 물었을 때 스킬 응답으로 확인한다. 비즈월렛과 이벤트 API는 이번 단계가 완료되고 성공한 다음 단계에서 구현한다
- 데이터 수집은 반드시 공식적으로 재사용이 허용된 공공데이터만을 사용해야 하며, 타 사이트의 무단 수집(크롤링)은 금지한다

### 2-5. 가정 및 종속성

- 공공데이터포털의 「전국농어촌체험휴양마을표준데이터」 오픈API가 지속적으로 제공된다고 가정한다
- 한국관광공사 TourAPI 서비스가 정상적으로 운영된다고 가정한다
- 카카오톡 플랫폼의 오픈빌더/스킬 API 정책이 개발 기간 중 크게 변경되지 않는다고 가정한다. 이번 단계에서는 이벤트 API를 호출하지 않는다
- 개발자가 기존에 보유한 Vercel 계정과 Supabase 계정을 그대로 활용할 수 있다고 가정한다
- 2026년 7월 광주·전남 행정통합에 따라 공공데이터의 행정구역 표기가 유동적일 수 있음을 전제로 하며, 이를 이중 필터링 방식으로 보완한다

## 3. 세부 요구사항 (Specific Requirements)

### 3-1. 외부 인터페이스 요구사항

#### 3-1-1. 사용자 인터페이스

| ID | 요구사항 |
|---|---|
| UI-01 | 웹 화면은 데스크톱 및 모바일 브라우저 모두에서 레이아웃이 깨지지 않고 표시되어야 한다 |
| UI-02 | 카카오톡 대화 화면은 카카오 i 오픈빌더가 제공하는 기본 템플릿(텍스트, 카드, 버튼)을 사용해 일관된 사용자 경험을 제공해야 한다 |
| UI-03 | 운영자가 사용하는 화면과 메시지는 타이핑 부담을 최소화하도록 버튼 선택 또는 사진/음성 전송 위주로 구성되어야 한다 |

#### 3-1-2. 하드웨어 인터페이스

본 소프트웨어는 특정 하드웨어에 종속되지 않으며, 표준 웹 브라우저 및 스마트폰에서 동작 가능해야 한다. 별도의 하드웨어 인터페이스 요구사항은 없다.

#### 3-1-3. 소프트웨어 인터페이스

| ID | 연동 대상 | 설명 |
|---|---|---|
| SI-01 | 공공데이터포털 OpenAPI | 「전국농어촌체험휴양마을표준데이터」를 HTTP GET 방식으로 호출 |
| SI-02 | 한국관광공사 TourAPI | 위치기반/지역기반 관광정보를 HTTP GET 방식으로 호출 |
| SI-03 | 카카오 i 오픈빌더 스킬 API | 카카오 서버로부터 HTTP POST 요청을 수신하고 정해진 JSON 형식으로 응답 |
| SI-04 | 카카오 이벤트 API | 이번 단계에서는 호출하지 않는다. 예약 안내는 스킬 API 응답으로만 한다. 비즈월렛과 이벤트 API는 이번 단계가 완료되고 성공한 다음 단계에서 구현한다 |
| SI-05 | LLM 제공자 API(Gemini/Claude/GPT) | 추상화 계층을 통해 선택된 하나의 LLM API에 HTTP 요청을 전송하고 텍스트 응답을 수신 |
| SI-06 | Supabase REST API | 마을 캐시, 예약, 후기 데이터를 저장·조회하기 위한 데이터베이스 인터페이스 |

#### 3-1-4. 통신 인터페이스

| ID | 요구사항 |
|---|---|
| CI-01 | 모든 외부 통신은 HTTPS 프로토콜을 사용해야 한다 |
| CI-02 | 카카오 스킬 API는 반드시 유효한 SSL 인증서를 갖춘 HTTPS 엔드포인트로 노출되어야 한다 |
| CI-03 | 내부 API(웹 화면용)는 JSON 형식으로 요청·응답을 주고받는다 |

### 3-2. 기능 요구사항 (Functional Requirements)

각 요구사항은 고유 ID를 부여한다. FR-01~FR-15는 기존 PRD 기능 항목과 대응하고, 카카오 역할 분기와 자가 등록처럼 이 문서에서 검증 단위로 나눈 항목은 FR-16부터 번호를 붙인다. 기존 번호는 바꾸지 않는다.

#### FR-01. 자연어 기반 마을 추천

| 항목 | 내용 |
|---|---|
| 설명 | 사용자가 자연어로 입력한 조건에 맞춰 광주·전남 지역 농촌체험마을을 추천한다 |
| 입력 | 자유 형식의 한글 텍스트 |

#### FR-08. 예약승인·예약거절

| 항목 | 내용 |
|---|---|
| 설명 | 예약 저장 값은 `pending`, `confirmed`, `rejected`만 가진다. 화면 문구는 대기, 승인, 거절이다. `운영자_예약관리`의 예약승인과 예약거절은 운영자용 단일 턴이고 서로 다른 블록이다. `decision` 파라미터는 없다. 승인인지 거절인지는 호출된 블록으로 확정한다 |
| 입력 | `booking_id`는 `@sys.number`다. 필수 파라미터가 아니다. 숫자가 있는 발화는 `7번 승인`, `7번 승인해줘`, `3번 예약 승인할게요`, `7번 거절`, `7번 거절해줘`, `3번 예약 거절할게요`다. 숫자 없는 발화 `승인할게요`, `거절할게요`도 받는다 |
| 처리 | `resolve_kakao_role`(FR-16)로 운영자 모드인지 확인한 뒤, 예약의 `village_id`가 일치할 때만 예약승인은 `confirmed`, 예약거절은 `rejected`로 갱신한다. `booking_id`가 없으면 예약승인은 `몇 번 예약을 승인하시겠어요? 예시: 7번 승인`, 예약거절은 `몇 번 예약을 거절하시겠어요? 예시: 7번 거절`만 반환하고 상태를 바꾸지 않은 채 종료한다. 관광객 모드, 미등록 사용자, 다른 마을 운영자의 변경은 거부한다. 관광객에게 이벤트 API로 결과를 푸시하지 않는다 |
| 출력 | `simpleText` |
| 우선순위 | 필수(Must Have, 2차 구현 대상) |
| 검증 기준 | 담당 운영자만 자기 마을 예약의 상태를 바꿀 수 있어야 한다. 관광객과 다른 마을 운영자의 변경 요청은 상태가 바뀌지 않아야 한다. 번호가 없는 요청은 안내만 하고 상태가 그대로여야 한다. 변경 직후 관광객에게 선톡이 가면 안 된다 |

#### FR-10. 예약 현황 조회 (푸시 미사용)

#### FR-15. 운영자 데이터 격리 (멀티테넌시)

| 항목 | 내용 |
|---|---|
| 설명 | AI사무장은 **추천봇(관광객)** 과 **마을별 AI사무장(운영자)** 두 역할을 겸하며, 운영자는 반드시 자기 `village_id`에 귀속된 데이터만 접근할 수 있어야 한다 |
| 배경 | 추천봇은 광주·전남 전체 마을을 비교·조회해야 하고, 운영자 AI사무장은 자기 마을 예약·후기·콘텐츠만 다뤄야 한다 |
| DB 요구 | `operators.village_id`는 NOT NULL FK다. `role=village`는 마을당 1명, `role=program`은 `(village_id, program_key)`당 1명, `kakao_user_id`는 UNIQUE다. `bookings`, `reviews`, `contents`는 `village_id` FK NOT NULL. `program_notes`와 `experience_calendar`도 `village_id`가 필수다 |
| 서버 요구 | 운영자용 API는 모든 쿼리에 `WHERE village_id = current_operator.village_id` 조건을 서버 단에서 강제 적용. 클라이언트가 전달한 `village_id`는 신뢰하지 않음 |
| 관광객 API | 추천·지도·주변정보 API는 기존처럼 전체 마을 데이터 읽기 전용 접근 유지 |
| 카카오 요구 | 역할 판별은 FR-16, 상태 변경 권한은 FR-08을 따른다. 예약 조회·승인/거절·홍보는 `role=village`만 한다. 체험 담당과 다른 마을은 거부한다 |
| LLM 요구 | 추천봇 프롬프트는 여러 마을 요약을 포함해 비교 추천. 운영자 AI사무장 프롬프트는 해당 `village_id` 마을 1건만 포함하고 다른 마을 정보는 절대 삽입하지 않음 |
| 우선순위 | 필수(Must Have) |
| 검증 기준 | 운영자 A가 마을 B의 예약·후기·콘텐츠·체험 글·달력을 직접 요청해도 조회·변경되지 않아야 한다. 체험 담당은 다른 체험 글과 달력·예약을 고치지 못한다. 관광객 추천 API는 여전히 전체 마을 비교가 가능해야 한다 |

#### FR-16. 카카오 사용자 역할 자동 분기

| 항목 | 내용 |
|---|---|
| 설명 | 하나의 카카오톡 챗봇이 스킬 요청마다 운영자(사무장)와 일반 사용자(관광객)를 가른다 |
| 입력 | 카카오 스킬 요청의 `userRequest.user.id` |
| 처리 | `resolve_kakao_role(user_id)`가 `userRequest.user.id`를 `operators.kakao_user_id`와 대조한다. 없으면 관광객 모드. 있으면 그 `village_id`와 `role`로 나눈다 |
| 출력 | 관광객 모드: 추천·예약 신청·후기·발화 `내 예약`. 마을 운영자: 예약 현황과 상태 변경(FR-08, FR-10), 체험 달력 등록. 체험 담당: 자기 체험 글 저장과 같은 마을 글·자기 체험 달력·예약 조회 |
| 예외 처리 | `user.id`가 없거나 `operators`에 없으면 운영자 기능(승인/거절, `예약 현황`)을 수행하지 않는다. `예약 현황`은 등록 안내, `내 예약`은 본인 예약 안내로 응답한다 |
| 우선순위 | 필수(Must Have, 2차 구현 대상) |
| 검증 기준 | 미등록 `user.id`는 관광객 응답만 반환하고 승인/거절은 거부해야 한다. `operators`에 등록된 `user.id`는 운영자 모드로 자기 마을 예약만 다뤄야 한다. 두 경우 모두 같은 채널의 스킬 요청이어야 한다 |

#### FR-17. 운영자 자가 등록

| 항목 | 내용 |
|---|---|
| 설명 | `운영자_등록`의 운영자 등록. 단일 턴. 아직 운영자가 아닌 사용자가 한 문장에 마을명과 코드를 넣어 자기 카카오 계정을 등록할 수 있다. 마을 운영자 예: `예시 갯벌마을 GB-001`. 체험 담당 예: `예시 갯벌마을 GB-001 갯벌체험`. 체험마다 발화를 추가하지 않는다. 지점이름은 `villages_cache.village_name`이다. `branch_name`은 없다 |
| 입력 | `village_id`는 커스텀 `village_name`의 대표값. `registration_code`는 `@sys.number`가 아니다. `program_label`은 `@sys.text`이고 필수 아님. 마을명이나 코드가 없으면 안내만 하고 종료. 패턴은 `{village_name} {registration_code}`와 `{village_name} {registration_code} {sys.text}`다. 세 번째 칸의 파라미터 이름은 `program_label`이다. `userRequest.user.id` |
| 처리 | 마을명이 `villages_cache.village_name` 하나와 일치하고, 코드가 그 행의 `registration_code`와 일치할 때만 `operators`에 `kakao_user_id`, `village_id`, `operator_name`, `registered_at`을 저장한다. 코드가 다르면 저장하지 않는다 |
| 출력 | 성공 시 등록 완료 안내 후 이후 요청부터 운영자 모드(FR-16). 실패 시 등록되지 않았음을 안내하고 관광객 모드를 유지한다 |
| 예외 처리 | 마을명과 코드가 없거나, 마을명이 없거나, 코드가 불일치하면 등록하지 않는다. 마을 운영자가 있는데 체험 이름이 없으면 등록하지 않는다. 그 체험에 담당이 있거나, 마을 글에 없는 체험이면 등록하지 않는다. 마을 운영자가 없는데 체험 이름만 있으면 등록하지 않는다 |
| 우선순위 | 필수(Must Have, 2차 구현 대상) |
| 검증 기준 | 한 문장의 올바른 마을명과 사전 정의 코드만 `operators` 행이 생겨야 한다. 코드가 다르면 행이 생기지 않고, 같은 `user.id`는 관광객 모드로 남아야 한다 |

#### FR-18. 세부 프로그램 운영 여부

| 항목 | 내용 |
|---|---|
| 설명 | 마을 한 행의 `program_name`을 괄호 밖 `+`와 줄바꿈으로 나눈 항목을 웹에 보여 준다. `program_name`이 비어 있으면 `program_type`을 같은 방식으로 나눈다. 운영자는 담당 마을 항목이 지금 운영 중인지 바로 바꿀 수 있다 |
| 입력 | 공개 읽기는 `village_id`. 운영자 변경은 `label`, `is_operating`. 본문의 `village_id`는 권한 판단에 쓰지 않는다 |
| 처리 | 상태 행이 없으면 운영 중이다. 변경은 `village_program_status`에만 저장하고 `villages_cache` 동기화는 이 표를 덮지 않는다. 끈 항목은 목록에 `지금은 운영하지 않음`으로 남는다. 마을 키는 `current_operator.village_id`만 쓴다 |
| 출력 | `GET /api/villages/{village_id}/promo`와 `GET /api/villages`의 `programs`는 `label`, `is_operating`이다. 마을 소개 화면에 그 목록이 나온다. 홈 카드는 운영 중인 항목만 짧게 보여 주고, 모두 꺼져 있으면 체험명 한 줄을 보여 준다. 카카오 마을 추천 `simpleText` 이유에 들어 있는 꺼진 항목은 `라벨은 지금은 운영하지 않음`으로 바뀐다. 이유에 없는 꺼진 항목은 나열하지 않는다 |
| 예외 처리 | 다른 마을 번호가 오면 403이다. 담당 마을 글에 없는 항목은 400이다. 가격·시간·새 프로그램 추가는 없다 |
| 우선순위 | 필수(Must Have) |
| 검증 기준 | 괄호 안 `+`는 한 항목이다. 상태 행이 없으면 운영 중이다. 운영자가 끄면 promo가 바로 `is_operating: false`다. 다른 마을 변경은 403이고, 동기화 후에도 끈 상태가 남는다 |

#### FR-19. 체험 글과 체험 달력

| 항목 | 내용 |
|---|---|
| 설명 | 한 마을의 여러 체험 글을 그 마을 운영자들이 함께 보고, 마을 운영자가 등록한 단체·인원 일정을 체험별로 본다. 체험 이름 예약은 그 날짜에 예약번호와 대기로 보인다 |
| 입력 | 체험 글 저장은 본문. 체험 달력 등록은 체험 이름, `visit_date`, 단체 이름, 인원. 예: `조개잡이 2026-11-01 광주소등학교 30명`. 본문·경로의 `village_id`는 권한 판단에 쓰지 않는다 |
| 처리 | 체험 담당만 자기 `program_key`를 `program_notes`에 저장한다. 마을 운영자만 `experience_calendar`에 넣는다. 같은 체험·날짜·단체는 인원만 바꾼다. 체험 담당은 자기 `program_key` 일정과 예약만 읽는다. 마을 운영자는 그 마을 일정과 예약을 모두 읽고 승인·거절한다. 체험 이름이 없는 예약은 `체험 미정`으로 마을 운영자 달력에만 나온다. 예약·후기·공개 홍보 쓰기는 마을 운영자만 유지한다 |
| 출력 | 카카오 `simpleText`. 한 줄은 체험 이름, 날짜, 단체, `N명`. `달력 열기`는 `/calendar/{token}`이다. 주소에 카카오 사용자 ID는 없다. 관광객 API와 `/village/{village_id}`에는 글과 달력을 넣지 않는다 |
| 예외 처리 | 다른 체험 글 수정, 체험 담당의 달력 등록·삭제와 예약 승인·거절, 다른 마을 조회는 거부한다. 단체나 인원이 없거나 마을 글에 없는 체험 이름은 저장하지 않는다 |
| 우선순위 | 필수(Must Have) |
| 검증 기준 | 체험 담당은 자기 글만 고치고 자기 체험 일정과 예약만 본다. 마을 운영자는 달력을 올리고 그 날짜의 예약을 승인·거절하며 체험 글은 읽기만 한다. 같은 날 다른 단체는 별도 일정이다. 다른 마을 글과 달력은 보이지 않는다. 체험 담당의 예약 승인은 상태를 바꾸지 않는다 |

### 3-4. 데이터 요구사항

| ID | 요구사항 |
|---|---|
| DR-01 | 마을 정보 테이블 이름은 `villages_cache`다. `village_id`는 마을 키, `village_name`은 후기 조회와 운영자 등록이 받는 마을명, `sido`·`sigungu`는 지역, `program_type`은 체험유형, `address`는 위치, `registration_code`는 운영자 등록 코드다. 공공데이터 원본 필드를 보존한다 |
| DR-02 | 예약 테이블 이름은 `bookings`다 (`reservations`가 아니다). `booking_id`는 예약 번호, `village_id`는 담당 마을, `customer_kakao_id`는 예약한 사람, `visit_date`는 방문일, `num_people`는 인원, `status`는 `pending`/`confirmed`/`rejected`(화면 문구 대기/승인/거절)다 |
| DR-03 | 후기 테이블 이름은 `reviews`다. `review_id`는 후기 키, `village_id`는 마을, `booking_id`는 연결된 예약, `rating`은 평점, `comment`는 본문, `sentiment`는 감성, `photo_url`은 선택 사진이다. 후기 조회는 `rating`과 `comment`를 안내한다 |
| DR-04 | 모든 데이터는 광주·전남 지역 마을과 연결되어야 하며, 지역 범위를 벗어나는 데이터는 저장되지 않아야 한다 |
| DR-05 | 동기화 이력은 실행 시각, 수신 건수, 필터링 후 건수, 성공 여부를 기록해야 한다 |
| DR-06 | 운영자 계정(`operators`)의 `operator_id`는 계정 키, `kakao_user_id`는 카카오 사용자 식별자(NOT NULL UNIQUE), `village_id`는 담당 마을(NOT NULL FK), `role`은 `village` 또는 `program`, `program_key`는 체험 담당만 채운다. 마을 운영자는 마을당 1명, 체험 담당은 체험당 1명이다. `operator_name`은 표시 이름, `registered_at`은 등록 시각이다. 웹 로그인(`login_id`)은 추가 수단이다. 자가 등록(FR-17)은 `registration_code`가 일치할 때만 연결한다 |
| DR-07 | 운영 콘텐츠(`contents`) 및 예약(`bookings`)·후기(`reviews`)는 반드시 `village_id` NOT NULL FK로 `villages_cache`에 연결되어야 하며, `village_id` 없는 레코드는 저장할 수 없어야 한다 |
| DR-08 | 체험 글(`program_notes`)은 마을·체험당 1건이다. 체험 달력(`experience_calendar`)은 같은 마을·체험·날짜·단체가 1건이다. `group_name`과 `num_people`이 있다. 둘 다 관광객 공개 API에 포함하지 않는다 |

## 5. 검증 및 인수 기준 (Verification & Acceptance Criteria)

| 구분 | 기준 |
|---|---|
| 기능 검증 | 3-2장에 정의된 각 기능 요구사항의 검증 기준을 모두 충족해야 한다 |
| 지역 정확성 검증 | 임의로 추출한 마을 데이터 20건 이상에 대해 수작업으로 광주·전남 소속 여부를 확인하여 필터링 결과와 대조한다 |
| 성능 검증 | 카카오 스킬 API 호출 100회 기준 5초 초과 응답이 5% 미만이어야 한다 |
| LLM 전환 검증 | 동일한 질의에 대해 Gemini와 Claude 각각으로 전환하여 정상적으로 추천 결과가 생성되는지 확인한다 |
| 장애 대응 검증 | 외부 API(TourAPI 등)를 의도적으로 차단한 상태에서도 웹 화면 나머지 기능이 정상 작동하는지 확인한다 |
| 보안 검증 | 환경변수 파일(.env)이 저장소에 커밋되지 않았는지, 동기화 엔드포인트가 인증 없이 호출되지 않는지 확인한다 |
| 데이터 격리 검증 | 서로 다른 `village_id`를 가진 운영자 계정으로, 운영자 A가 마을 B의 예약·후기·콘텐츠·체험 글·달력을 직접 조회·변경 요청했을 때 모두 거부되는지 확인한다. 체험 담당은 다른 체험 글과 달력 등록·예약 승인을 하지 못해야 한다 |
| 역할 분기 검증 | 같은 채널에서 미등록 `user.id`는 관광객 모드, `operators`에 있는 `user.id`는 운영자 모드로 응답하는지 확인한다 |
| 자가 등록 검증 | 한 문장의 마을명과 코드가 사전 정의 코드와 일치할 때만 등록되고, 불일치하면 `operators`에 행이 생기지 않는지 확인한다 |
| 승인·거절 블록 검증 | 예약승인과 예약거절은 서로 다른 블록이다. `booking_id`가 없으면 안내만 하고 상태는 그대로다 |
| 알림 방식 검증 | 예약 접수·승인 직후 선톡이 나가지 않아야 한다. 운영자 `예약 현황`만 자기 마을 예약을 안내하고, 관광객 `내 예약`은 본인 예약만 안내하는지 확인한다 |
| 검색 수집 검증 | 네이버에 알리는 주소는 `/`, `/recommend`, `/map`, `/nearby`, `/villages`, `/dashboard`다. 운영자 화면, 달력 토큰, 개발 화면은 수집하지 않는다 |
