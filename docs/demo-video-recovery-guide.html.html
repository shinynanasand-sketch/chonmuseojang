총괄 재정비 및 작업 복구 명세

현재 진행된 작업을 조사하고, 기존 계획과의 차이 및 오류를 확인한 뒤 필요한 부분만 복구하기 위한 새 총괄 에이전트의 작업 기준이다.

새 프로젝트를 처음부터 만드는 문서가 아니다.

기존 코드·영상·편집 데이터·승인 내용을 보존한다. 실제 상태를 먼저 확인하고 유지·수정·재촬영·재편집 범위를 결정한다.

문서의 계획과 실제 진행 상태는 다를 수 있다.

아래 클립 구성과 폴더 구조는 기준안이다. 현재 작업을 조사하기 전에는 완료 여부나 실제 위치를 단정하지 않는다. 사용자가 승인한 변경사항과 확인된 실제 자료를 함께 검토한다.

1. 새 총괄의 임무

  1. 현재 작업 위치와 사용 중인 프로젝트를 확인한다.
  2. 문서·코드·소재·편집 결과·오류 기록을 조사한다.
  3. 기존 계획과 실제 상태의 차이를 정리한다.
  4. 유지 가능한 작업과 재작업이 필요한 작업을 구분한다.
  5. 영향 범위와 복구 순서를 제안한다.
  6. 사용자 승인 후 최소 범위로 수정한다.
  7. 검증 결과와 인계 문서를 갱신한다.
  8. 클립 담당과 최종 조립 작업을 다시 연결한다.

이전 대화를 모두 알고 있다고 가정하지 않는다. 파일에 없는 결정과 승인 내용은 사용자에게 확인한다.

2. 유지할 촬영 원칙

2.1 환경과 역할

  • 보조 모니터 없는 노트북이다.
  • PC 카카오톡과 실제 연결된 Chrome만 OBS 창 캡처한다.
  • 카카오톡과 웹앱은 사람이 직접 조작한다.
  • 녹화 시작·종료는 검증된 OBS 단축키 또는 수동 조작을 사용한다.
  • 터미널 Enter로 한 줄씩 진행하는 방식은 기본 운영에서 제외한다.
  • 실제 운영에서는 계정당 한 역할이다.
  • 시연 계정의 역할을 순차 전환한다.
  • 같은 예약을 체험객·사무장·체험 담당 관점에서 확인한다.

2.2 시연 데이터 기준

  • 대상 마을: 예시 갯벌마을
  • 예약 체험: 갯벌체험
  • 기본 입력: 단체 이름 없음 / 10:00 / 4명
  • 변경 제안 시간: 11:00
  • 홍보 사진: docs_1/sample.jpg
  • 중지 대상: 조개잡이만
  • 담당 배정: 시연 담당에게 갯벌체험·소금체험
  • 일정 절차: 사무장 제안 → 체험객 동의 → 사무장 최종 승인

위 값이 실제 촬영에서 변경됐다면 불일치로 기록하고 사용자에게 확인한다. 기존 영상을 억지로 위 값에 맞춰 폐기하지 않는다.

2.3 금지사항

  • 카카오톡 클릭·입력·메시지 발송 자동화
  • 도선국사마을 예약 열람
  • 관광객에게 공개 버튼 클릭
  • 갯벌체험 중지
  • 비밀번호 파일 열람·비밀번호와 토큰 기록
  • 확인하지 않은 알림 전달·현장 효과 주장
  • 사용자 승인 없는 운영 데이터 변경

3. 조사 전에는 변경하지 않는다

첫 진단 단계는 읽기 중심으로 진행한다.

파일 이동·삭제·덮어쓰기, 패키지 설치, 자동 수정, DB 실행, 예약 생성, 사진 재전송, 저장 상태 초기화는 하지 않는다.

  • 기존 폴더가 있다는 이유로 새 구조로 이동하지 않는다.
  • 현재 의존성을 확인하기 전에 새 프로젝트를 생성하지 않는다.
  • 오류를 확인하지 않고 패키지를 일괄 업데이트하지 않는다.
  • 미커밋 변경사항을 다른 에이전트의 실수라고 단정하지 않는다.
  • Git 초기화·강제 되돌리기·일괄 정리를 하지 않는다.
  • 촬영 품질 문제를 이유로 저장 작업을 다시 수행하지 않는다.
  • 영상 파일이 존재한다는 이유로 재생과 내용을 확인했다고 보고하지 않는다.

4. 현재 상태 조사 항목

영역확인 내용주의
작업 위치 현재 워크스페이스, 영상 프로젝트, 웹앱 위치 새 폴더 생성보다 기존 위치 확인 우선
문서 대본, 편집안, 스타일, 진행 상태, 인계 기록 날짜만으로 최신 결정이라고 판단하지 않음
코드 Remotion 구조, 공통 부품, 클립 데이터, 변경사항 진단 중 수정하지 않음
의존성 package.json, 잠금 파일, 실행 스크립트, 버전 설치·업데이트는 별도 승인
원본 클립별 테이크, 길이, 해상도, 재생 여부 메타데이터 확인과 화면 확인 구분
편집 결과 검토 영상, 최종 영상, 사용 소재와 대응 관계 출력 존재와 사용자 승인 구분
오류 메시지, 발생 단계, 재현 조건, 영향 범위 최초 원인과 후속 오류 구분
서비스 상태 현재 역할, 예약번호, 일시, 상태, 배정, 운영 상태 사용자 확인 또는 승인된 검증으로 확인
승인 클립·스타일·소재·편집 결과의 승인 여부 기록 없으면 미확인

확인 수준

  • 파일로 확인: 내용과 존재를 확인함
  • 실행으로 확인: 실제 동작을 확인함
  • 사용자 확인: 사용자가 상태를 알려줌
  • 미확인: 근거가 부족함

5. 계획과 실제 상태의 차이 기록

차이가 있다고 모두 오류는 아니다. 이미 승인된 개선, 작업 중 임시 변경, 실제 오류를 구분한다.

ID기준 계획실제 상태 분류처리 제안
D-001 확인 후 기입 확인 후 기입 미확인 사용자 확인

분류 기준

  • 승인된 변경 — 현재 작업 유지, 명세 갱신
  • 기록 누락 — 실제 상태와 승인 확인 후 기록 보완
  • 구현 오류 — 영향 범위 확인 후 수정
  • 촬영 오류 — 활용 가능 범위 확인 후 부분 재촬영 검토
  • 편집 오류 — 원본 유지, 편집 데이터·코드 수정
  • 데이터 불일치 — 추가 저장 없이 원인 확인
  • 미확인 — 근거 확보 전 결론 보류

6. 오류와 재작업 판정

문제우선 조치재촬영 판단
자막 시간·문구·확대 위치 오류 편집 데이터 수정 보통 불필요
폰트·패키지·렌더링 오류 최소 재현 및 코드·환경 수정 원본이 정상이면 불필요
역할 라벨 오류 실제 역할 확인 후 라벨 수정 실제 시연 역할도 틀렸다면 검토
개인정보 노출 제외·가림 처리 가능성 검토 안전한 제거가 불가능하면 필요
클릭·연결·결과 화면 누락 다른 테이크와 보충 화면 확인 핵심 동작 증명이 안 되면 부분 촬영
예약번호·일시·상태 불일치 소재와 실제 상태 추적 맞지 않는 장면만 검토
웹앱 자체 기능 오류 영상 작업과 분리해 보고 서비스 수정 승인·검증 후 검토
가장 작은 복구 범위를 선택한다.

데이터 수정 → 코드 수정 → 재렌더링 → 보충 촬영 → 클립 재촬영 → 전체 재촬영 순서로, 해당 문제에 적합한 방법을 검토한다. 이 순서는 강제 규칙이 아니라 불필요한 재작업을 줄이기 위한 판단 기준이다.

오류 기록 필수 항목

  • 오류 ID와 발생 단계
  • 정확한 메시지 또는 화면 증상
  • 재현 조건과 예상 결과
  • 실제 결과
  • 영향받는 파일·클립·데이터
  • 원인 확인 수준
  • 수정안·검증 방법·되돌릴 방법

7. 폴더와 문서 재정비

다음은 목표 역할 구조다. 실제 경로가 다르면 먼저 대응표를 작성하고 기존 위치를 유지한다. 사용자가 승인하기 전에는 파일을 이동하지 않는다.

동일 역할의 문서가 이미 있으면 새 문서를 중복 생성하지 않는다. 기준 문서를 정하고, 오래된 문서는 보관 또는 참조 처리한다.

8. 총괄과 개별 에이전트 운영

8.1 새 총괄

  • 현황 조사와 계획 차이 판정
  • 공통 오류와 공통 컴포넌트 수정 관리
  • 복구 우선순위·작업 범위 승인 요청
  • 클립 담당 재배정
  • 최종 연결·회귀 검증

8.2 클립 담당

  • 자기 클립의 소재·데이터·전용 코드 검토
  • 승인된 범위만 수정
  • 공통 파일은 직접 수정하지 않고 총괄에 제안
  • 작업 후 오류 상태·클립 상태·인계 기록 갱신

8.3 사용자

  • 실제 촬영과 서비스 조작
  • 현재 데이터·과거 승인 내용 확인
  • 복구 범위·재촬영·최종 결과 승인

별도 대화는 사용할 수 있으나, 같은 작업 폴더의 수정은 순차적으로 진행한다. 새 총괄 진단 중에는 다른 담당의 파일 수정을 중단한다.

9. 클립 기준과 현재 상태표

클립기준 범위현재 상태
A대본 1~3 / 체험객 예약조사 후 기록
B대본 4~6 / 홍보 초안조사 후 기록
C대본 7~8 / 운영·담당 배정조사 후 기록
D대본 9~11 / 조회·일정 제안조사 후 기록
E대본 12~13 / 변경 동의·최종 승인조사 후 기록
F대본 14~15 / 담당 조회조사 후 기록

실제 클립 구분이 다르면 대응 관계를 정리한다. 이름이 다르다는 이유로 소재를 다시 촬영하거나 이름을 일괄 변경하지 않는다.

진행 상태와 복구 상태는 분리한다

  • 촬영: 미진행 / 촬영됨 / 내용 확인됨
  • 편집: 미진행 / 작업 중 / 검토 가능
  • 승인: 미확인 / 미승인 / 승인
  • 복구: 판정 전 / 불필요 / 필요 / 작업 중 / 검증 완료

“완료” 한 단어로 촬영·편집·승인·오류 해결을 모두 표현하지 않는다. 이전에 승인된 작업도 수정 후에는 영향받은 부분을 다시 검증한다.

10. 복구 단계와 승인 지점

  1. 진단: 읽기 중심 현황 조사
  2. 판정: 차이·오류·유지 가능한 작업 분류
  3. 승인: 수정 파일·재촬영·데이터 작업 범위 결정
  4. 보존: 기존 결과와 변경사항의 복원 지점 확보
  5. 복구: 한 문제 또는 한 클립씩 수정
  6. 검증: 수정 부분과 영향받는 다른 부분 확인
  7. 재개: 남은 클립 또는 전체 조립 진행

백업·Git 기록 방식은 현재 저장소 상태를 확인한 뒤 결정한다. 비밀정보나 대용량 원본을 무조건 커밋하지 않는다. 기존 결과를 덮어쓰는 대신 새로운 검토 결과로 비교한다.

재개 위치는 현재 상태에 따라 정한다.

클립 A부터 무조건 다시 시작하지 않는다. 이미 쓸 수 있는 클립은 유지하고 필요한 작업부터 이어간다.

11. 새 총괄 시작 프롬프트

너는 체험마을 AI사무장 시연 영상의 새 총괄 에이전트다.

이 HTML은 기존 작업을 진단하고 복구하기 위한 명세다.
처음부터 프로젝트를 다시 만드는 지시가 아니다.

현재 작업은 이전 계획과 일부 다를 수 있다.
중간 오류, 미완료 작업, 이미 승인된 변경도 있을 수 있다.

첫 작업은 읽기 중심의 현황 조사만 진행한다.

확인:
1. 실제 작업 폴더와 영상 프로젝트 위치
2. 기존 문서와 승인 기록
3. Remotion 코드·의존성·클립 데이터
4. 원본·검토 영상·선택된 소재
5. 기존 오류 메시지와 미해결 항목
6. 계획과 실제 진행의 차이
7. 현재 데이터 상태 중 확인된 것과 미확인인 것

규칙:
- 파일을 이동·삭제·덮어쓰지 않는다.
- 패키지 설치·업데이트를 하지 않는다.
- 기존 서비스 코드를 변경하지 않는다.
- DB·예약·사진 전송·운영 상태 변경을 하지 않는다.
- 비밀번호 파일과 토큰을 읽거나 출력하지 않는다.
- Git 변경사항을 되돌리거나 정리하지 않는다.
- 영상 확인이 불가능하면 그 한계를 명시한다.
- 이전 대화와 승인을 알고 있다고 가정하지 않는다.
- 현재 진행 상태를 임의로 완료·승인으로 기록하지 않는다.
- 다른 담당 에이전트와 동시에 파일을 수정하지 않는다.

먼저 대화에 다음을 보고한다.
A. 실제 작업 위치와 자료 목록
B. 계획과 현재 상태의 차이
C. 오류와 미확인 항목
D. 유지 가능한 작업
E. 필요한 재작업 후보
F. 사용자에게 필요한 확인
G. 최소 범위 복구 계획 초안

보고 후 멈춘다.
문서 작성과 코드 수정은 내 승인 후 진행한다.

12. 진단 후 문서 정리 프롬프트

현황 조사 결과를 확인했다.

이번에는 승인한 범위에서 진단·인계 문서만 정리해줘.
코드·소재·의존성·서비스 데이터는 변경하지 않는다.

- 기존 문서가 있으면 재사용한다.
- 실제 경로 대응표를 만든다.
- 계획 차이와 오류 목록을 기록한다.
- 유지·수정·재촬영·재편집 후보를 구분한다.
- PROJECT_STATUS와 DATA_STATE의 확인 수준을 명시한다.
- 승인 기록이 없으면 미확인으로 남긴다.
- 최신 데이터 상태와 과거 촬영 상태를 분리한다.
- 재작업마다 영향 범위·검증 방법·복원 방법을 적는다.

작성한 문서와 남은 의사결정을 보고한 뒤 멈춘다.

13. 개별 복구 작업 프롬프트

이번 작업은 [오류 ID 또는 클립 이름]의 복구만 담당한다.

먼저 읽을 자료:
- 공통 작업 명세
- 현황 조사 결과
- 오류 목록
- 승인된 복구 계획
- 해당 클립 문서
- 공통 스타일과 현재 데이터 상태

수정 범위:
[승인한 파일과 작업]

수정 금지:
[다른 클립·공통 파일·서비스 코드 등]

진행:
1. 오류와 재현 조건 확인
2. 최소 수정안 제시
3. 승인된 범위만 수정
4. 해당 문제 검증
5. 영향받는 다른 구간 회귀 검증
6. 결과와 미검증 기록

공통 파일 수정이 필요하면 직접 변경하지 말고 보고한다.
추가 촬영이나 저장 상태 변경이 필요하면 사용자 승인을 요청한다.
정상 원본은 유지하고 기존 승인 결과를 덮어쓰지 않는다.
문제가 해결됐다는 근거와 남은 한계를 보고한다.

14. 총괄 재개·최종 조립 프롬프트

승인된 복구 작업을 마쳤다.
현황과 남은 작업을 다시 확인하고 재개 위치를 제안해줘.

확인:
- 열린 오류와 해결된 오류
- 클립별 촬영·편집·승인·복구 상태
- 실제 사용 소재와 편집 데이터
- 공통 스타일과 프로젝트 구조
- 예약번호·일시·상태 연결
- 역할 표시와 변경 승인 절차

이미 정상인 작업은 다시 만들지 않는다.
남은 클립 작업이 있으면 해당 담당에게 인계한다.
전체 조립이 가능하면 연결·렌더링·최종 검증 계획을 제안한다.

최종 렌더링은 사용자 승인 후 진행한다.
실행으로 확인한 것과 미검증을 구분해 보고한다.

가능한 자료부터 제공한다. 없는 자료를 억지로 만들 필요는 없다.

  • 기존 작업 문서와 최신 대본

  • 오류가 발생한 단계
  • 촬영된 클립과 선택된 테이크
  • 검토용 영상과 사용자 승인 내용

  • 이미 바뀐 운영 상태·담당 배정·홍보 초안
