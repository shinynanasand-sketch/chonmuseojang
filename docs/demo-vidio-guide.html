체험마을 AI사무장
시연 영상 제작 가이드

보조 모니터 없는 노트북에서 PC 카카오톡과 Chrome을 함께 촬영하고, 같은 예약을 세 역할의 관점으로 보여주기 위한 실행 문서다.

단일 모니터 OBS 창 캡처 수동 시연 Remotion 편집 Cursor 프롬프트 포함 실행 전 검증 필요

핵심 작업 방식

짧은 클립별 대본 확인 → 대본·Cursor 최소화 → OBS 녹화 시작 → 사람이 시연 → 녹화 종료 → 결과 확인 → Remotion 편집

검증 상태

이 문서는 촬영·편집 계획이다. 실제 배포, DB 적용, 권한, 화면 문구, 녹화 및 렌더링 결과는 사용자 환경에서 확인해야 한다. 문서에 적혀 있다는 이유만으로 실행 성공을 가정하지 않는다.

1. 목적과 불변 원칙

1.1 영상의 목적

  • 카카오 메뉴에서 웹앱으로 연결되는 흐름을 보여준다.
  • 체험객의 예약과 사무장의 관리 과정을 보여준다.
  • 홍보 초안, 프로그램 중지, 복수 체험 배정을 보여준다.
  • 일정 제안 → 체험객 동의 → 사무장 확정을 구분한다.
  • 체험 담당자의 조회 전용 화면을 보여준다.

1.2 시연 방식

같은 예약 한 건을 체험객, 사무장, 체험 담당 관점에서 순차적으로 보여준다. 운영에서는 계정당 한 역할이며, 시연에서만 전용 계정의 역할을 전환한다.

1.3 시작 카드

실제 운영에서는 계정당 한 역할을 사용합니다.
이 영상은 시연 계정의 역할을 순차 전환해 보여드립니다.
세 사람이 동시에 대화하는 장면이 아닙니다.

한 화면이 길어지면 두 카드로 나눈다. 읽을 수 있는 표시 시간은 시험 렌더링에서 확인한다.

1.4 절대 하지 않는 작업

  • 카카오톡 클릭·키 입력·메시지 발송 자동화
  • 기존 서비스와 운영 권한 정책의 임의 변경
  • 도선국사마을 예약 열람
  • 비밀번호를 문서·코드·프롬프트에 기록
  • 사용자 승인 없는 DB 실행·실제 데이터 변경
  • 관광객에게 공개 버튼 클릭
  • 갯벌체험 중지
  • 확인하지 않은 기능·효과·알림 전달을 자막으로 주장

3. 단일 모니터 촬영 운영

3.1 창 배치

  • 왼쪽: PC 카카오톡의 실제 시연 채팅창
  • 오른쪽: 카카오 메뉴에서 연결되는 Chrome
  • OBS: 두 창을 각각 창 캡처 소스로 구성
  • Cursor·대본·터미널: 캡처 대상 제외, 촬영 중 최소화

카카오 영역 약 30~35%, Chrome 약 65~70%를 시작점으로 검토한다. 실제 글씨와 반응형 화면을 확인하고 비율을 조정한다.

출력 해상도만 높여도 원본 글씨가 선명해지는 것은 아니다. 노트북 화면에서 확보한 실제 가독성이 기준이다. Chrome 폭을 줄였을 때 모바일형 레이아웃으로 바뀌는지도 확인한다.

3.2 대본 확인

  1. 촬영할 클립의 큐시트를 읽는다.
  2. 현재 역할·마을·시작 화면·risk를 확인한다.
  3. 대본과 Cursor를 최소화한다.
  4. 시연할 창을 활성화한다.
  5. OBS 녹화를 시작하고 시연한다.

휴대폰이나 종이 큐시트를 사용할 수 있으면 편리하다. 없어도 짧은 클립별로 대본을 읽고 촬영하면 된다. 중간에 대본을 확인한 구간은 편집에서 제외한다.

3.3 OBS 녹화 시작·종료

  • OBS 설정의 단축키에서 녹화 시작·종료를 지정한다.
  • 카카오톡·Chrome·노트북 기능키와 충돌하는지 시험한다.
  • Enter는 녹화 단축키로 사용하지 않는다.
  • 단축키가 안 되면 OBS에서 직접 시작하고 최소화한다.
  • 촬영 종료 시 OBS를 열어 종료하고 앞뒤 구간을 편집한다.

OBS를 최소화하고 다른 앱이 활성화된 상태에서도 단축키가 동작하는지 실제로 확인해야 한다.

3.4 첫 시험 녹화

  • 10~20초 동안 두 창을 녹화했다.
  • 카카오와 Chrome을 오가도 두 소스가 정상 기록된다.
  • 마우스 포인터가 의도대로 보인다.
  • 카카오 링크가 여는 Chrome이 캡처 대상과 같다.
  • 대본·OBS·Cursor를 열었다 닫아도 캡처 상태가 정상이다.
  • 파일 선택창의 포함 여부를 확인했다.
  • 녹화 파일을 재생해 글씨·프레임·노출 정보를 확인했다.

창 캡처의 가림·최소화·팝업 동작은 환경에 따라 다를 수 있다. 정상 동작을 가정하지 말고 시험한다. 시연 대상인 카카오톡과 Chrome은 촬영 중 최소화하지 않는다.

4. 촬영 전 확인

4.1 배포·역할·날짜

  • 촬영할 코드가 배포되어 있다.
  • supabase/demo_sessions.sql의 적용 여부를 확인했다.
  • SQL 변경이 필요하면 사용자 승인 후 수행한다.
  • 선택한 시연 역할이 유지되는지 확인했다.
  • 카카오 메뉴 갱신용 버튼의 정확한 이름을 확인했다.
  • 원래 날짜가 예약 현황 조회 기간 안에 있다.
  • 원래·변경 날짜가 갯벌체험 예약 가능한 조건이다.
  • 변경 승인 페이지의 실제 권한 조건을 확인했다.

4.3 로그인·비밀번호

  • 내 마을 로그인 아이디: owner_v001
  • 비밀번호는 사람이 녹화 전에 캡처되지 않는 곳에서 확인한다.
  • Cursor는 운영자 비밀번호 파일을 열거나 읽지 않는다.
  • 가능하면 로그인 완료 화면부터 촬영한다.
  • 로그인 장면이 필요하면 비밀번호 입력 구간은 편집에서 제외한다.
  • 아이디를 공개 영상에 표시해도 되는지 확인한다.

4.4 risk 작업

대본 3·6·7·8·11·12·13번은 저장 또는 상태 변경이 발생한다. 해당 클립 시작 전에 대상과 현재 상태를 다시 확인한다.

저장 후 녹화가 마음에 들지 않아도 같은 작업을 바로 반복하지 않는다. 중복 예약, 재전송, 운영 상태 반전, 반복 일정 변경을 먼저 방지한다.

6. 역할별 촬영 대본

달력 연결 장면 공통 규칙

카카오 달력 버튼을 누르기 전에 Chrome은 달력이 아닌 화면으로 둔다. 버튼 클릭 후 실제 화면이 바뀌는 모습을 남긴다. 카카오 버튼 이름과 웹 제목이 함께 보이도록 잠시 유지한다.

클립 A — 체험객 예약

1. 체험객 역할 전환

카카오의 시연 역할 → Chrome의 체험객을 선택한다.

확인:

  • 지금 역할은 체험객입니다.
  • 체험객으로 바꿨습니다. 예약하기와 내 예약을 씁니다.

사전 확인한 메뉴 갱신용 카카오 버튼을 한 번 누른다. 체험객 역할 문장과 새 버튼을 확인한다.

메뉴 갱신용 버튼 이름: ________________________________

2. 예약 달력 연결

시작: 오른쪽은 시연 역할 화면.

카카오 예약하기 → 예시 갯벌마을 카드 → 달력으로 예약.

확인: Chrome이 해당 마을 예약 달력으로 바뀜. 버튼과 달력 제목을 함께 보여준다.

금지: 이 연결 장면에서는 예약 제출하지 않음.

3. 예약 접수 risk

미리 정한 빈 날짜 → 갯벌체험 → 단체 이름 없음 → 10:00 → 4명 → 이 날짜에 예약.

확인: 예약번호·접수 결과·목록의 대기 상태. 번호와 일시를 기록하고 결과 화면을 유지한다.

실패: 다시 제출하지 않고 예약 생성 여부부터 확인.

클립 B — 사무장 홍보

4. 사무장 역할 전환

시연 역할 → 사무장 → 메뉴 갱신.

  • 지금 역할은 사무장입니다.
  • 사무장으로 바꿨습니다. 예약 현황, 달력, 홍보 사진을 씁니다.
  • 카카오의 역할 문장과 새 버튼 확인.

5. 내 마을

Chrome에서 내 마을을 열고 사람이 로그인한다. 예시 갯벌마을 운영 현황을 확인한다.

로그인 자체가 핵심이 아니면 완료 화면부터 사용한다. 비밀번호 입력 구간은 공개 영상에서 제외한다.

6. 홍보 초안 risk

카카오 홍보 사진 → docs_1/sample.jpg 선택 → 사람이 전송.

확인: 카카오에 소개글·SNS 홍보문구, 내 마을에 같은 초안 표시.

금지: 관광객에게 공개를 누르지 않음. 초안이 안 나오면 재전송하지 않고 중단.

클립 C — 체험 운영과 담당 배정

7. 조개잡이 중지 risk

프로그램에서 조개잡이의 중지를 누른다.

확인: 조개잡이 버튼은 운영으로 바뀜. 갯벌체험 버튼은 중지인 상태로 유지.

금지: 갯벌체험 중지 클릭.

8. 담당 체험 배정 risk

체험 담당의 시연 담당 카드 → 갯벌체험 검색·선택 → 소금체험이 없으면 추가 → 저장.

확인: 체험 담당을 저장했습니다. 카드에 두 체험 표시.

클립 D — 예약 확인과 변경 제안

9. 예약 현황

카카오 예약 현황 조회를 누른다.

확인: 조회 기간의 답에 같은 예약번호와 대기 상태.

실패: 새 예약을 만들지 않고 날짜·조회 기간 확인.

10. 사무장 달력 연결

시작: 시연 역할 화면 또는 내 마을.

카카오 체험 달력 조회 → 달력 열기.

확인: 예시 갯벌마을 예약 승인 화면. 같은 예약에 승인·거절·일정 변경 버튼.

버튼과 웹 제목을 함께 보여준다. 이 연결 장면에서는 관리 버튼을 누르지 않는다.

11. 다른 일시 제안 risk

같은 예약의 일정 변경 → 미리 정한 다른 날짜 → 11:00 → 이 날짜로 제안.

확인: 일정 변경을 제안했습니다.

금지: 변경 승인 주소 추정·직접 생성.

클립 E — 체험객 동의와 사무장 확정

권한 사전 확인: 변경 승인 페이지에 체험객 역할이 필요한지 확인한다. 필요하면 체험객으로 전환하고 이후 사무장으로 복귀한다. 예약별 승인 링크라면 실제 권한 조건에 맞춰 진행한다.

영상의 업무 주체 표시와 실제 로그인 역할을 혼동하지 않는다.

12. 체험객 변경 동의 risk

같은 대화에 실제 도착한 링크를 Chrome에서 연다. 예약번호와 제안 일시 확인 → 변경 승인.

확인: 변경을 승인했습니다. 예약은 대기입니다. 변경 일시도 실제 반영됐는지 확인한다.

실패: 링크가 안 오면 주소를 만들지 않고 중단.

13. 사무장 최종 승인 risk

필요하면 사무장 복귀 → 사무장 달력 → 같은 예약번호·변경 일시 확인 → 승인.

확인: 예약 상태가 승인으로 바뀜.

체험객 변경 승인 = 일정 동의
사무장 최종 승인 = 예약 확정

클립 F — 체험 담당 조회

14. 체험 담당 역할 전환

시연 역할 → 체험 담당 → 메뉴 갱신.

  • 지금 역할은 체험 담당입니다.
  • 체험 담당으로 바꿨습니다. 달력은 보기만 합니다.
  • 카카오 역할 문장과 새 버튼 확인.

15. 담당 달력 연결

시작: 오른쪽은 시연 역할 화면.

카카오 체험 달력 조회 → 달력 열기.

확인: 제목 체험 일정. 같은 예약번호·최종 일시 표시. 승인·거절·일정 변경 버튼 없음.

연결 장면과 조회 전용 화면을 각각 충분히 남긴다.

7. 촬영 중 확인할 짧은 큐시트

휴대폰·종이로 보거나, 클립 시작 전에 읽고 대본 창을 최소화한다.

클립짧은 순서핵심 확인·중단 조건
A 체험객 역할 → 메뉴 갱신 → 예약 달력 → 입력 → 접수 예약번호·일시·대기. 생성 실패 시 재제출 금지.
B 홍보 사무장 → 내 마을 → 사진 전송 → 두 화면 초안 공개 금지. 결과 없으면 재전송 금지.
C 운영 조개잡이 중지 → 담당 두 체험 → 저장 갯벌체험 운영 유지. 두 체험 저장 확인.
D 제안 같은 예약 조회 → 달력 연결 → 다른 일시 제안 예약번호 일치. 주소 추정 금지.
E 승인 실제 링크 → 변경 동의 → 대기 → 사무장 승인 권한·변경 일시 확인. 링크 없으면 중단.
F 담당 담당 역할 → 메뉴 갱신 → 달력 연결 같은 예약·최종 일시. 관리 버튼 없음.

각 클립 공통 순서

  1. 현재 역할·데이터·시작 화면·risk 확인
  2. 대본 최소화, 시연 창 활성화
  3. 녹화 시작 후 2~3초 여유
  4. 시연 수행
  5. 결과 화면 3~5초 여유
  6. 녹화 종료와 재생 확인
  7. 예약 기록·촬영 메모 업데이트

8. 장면·자막 편집안

촬영 클립과 최종 편집 장면은 다르다. 기존 클립 안에서 여러 장면을 나눠 사용한다. 대본만으로 타임코드를 확정하지 않는다.

장면원본자막 초안화면
예약 연결A-2 카카오에서 ‘달력으로 예약’을 누르면 웹 예약 달력이 열립니다. 두 창 → 웹 확대

8.1 확인 후 추가하는 설명

  • 비공개: “공개하기 전에는 홍보 초안이 마을 소개에 표시되지 않습니다.” 실제 동작 확인 후 사용.
  • 개선 배경: “여러 체험을 맡는 현장 의견을 반영해 복수 배정으로 개선했습니다.” 인터뷰·개발 이력으로 확인 후 사용.
  • 담당 권한: “승인과 일정 변경은 하지 않습니다.” 화면과 권한 검증 후 사용.

8.2 역할·자막 디자인

  • 상단: 역할명 + 시연 계정
  • 하단: 최대 두 줄, 주요 버튼과 입력칸을 가리지 않음
  • 색상만으로 역할을 구분하지 않음
  • 변경 동의는 실제 구현에 맞춰 체험객 응답 시연으로 표시
  • 조작 설명·결과 설명·개선 배경을 구분
  • 긴 문장은 여러 화면으로 나눔
  • 과도한 흔들림·바운스 효과 제외

9. Remotion 작업 기준

9.1 구현 순서

  1. 사용 조건·라이선스·설치 환경 확인
  2. 원본 영상 길이·해상도·코덱 확인
  3. 원본 재생만 검증
  4. 20~30초 구간에 자막·역할 표시
  5. 실제 영상 기준 확대 적용
  6. 시험 렌더링·사용자 검토
  7. 승인 후 전체 확장

9.2 레이어

  • 원본 영상: 확대 대상
  • 역할 표시: 확대 영향 없음
  • 설명 자막: 확대 영향 없음
  • 강조 효과: 실제 위치·시점 확인 후
  • 전환 카드: 역할 변경 사실 표시

9.3 데이터 관리

클립 이름, 대본 번호, 역할, 자막, 시간, 확대 영역, 절단 구간, 검증 상태를 코드와 분리한다.

  • 영상 확인 전 시간·좌표: 미정
  • 확인 후: 실제 영상에 맞춰 확정
  • 확대 좌표: OBS 최종 영상 기준
  • 원본을 자르면 시간 매핑도 수정
  • 실제 클릭과 일치하지 않는 포인터 효과를 만들지 않음

9.4 Playwright 보충 조건

웹 글씨가 너무 작거나 반복 검증이 필요한 경우에만 승인 후 사용한다. 카카오 링크 연결 장면은 실제 OBS 녹화를 유지한다.

  • 같은 역할·마을·예약번호·데이터 상태로 보충
  • 별도 촬영을 무편집 연속 실행처럼 표현하지 않음
  • 웹 상세 보기 장면으로 구분 가능
  • 카카오 PC 앱 자동 조작에 사용하지 않음

10. Cursor 프롬프트

HTML 문서를 프로젝트에 직접 저장하고 파일을 참조시킨다. Cursor가 파일 내용을 읽었는지 확인한 뒤 아래 프롬프트를 단계별로 전달한다. 한 번에 전체 작업을 실행시키지 않는다.

프롬프트 1 — 실행 전 검토

이 HTML 문서를 체험마을 AI사무장 시연 영상의 작업 명세로 읽어줘.

촬영 환경은 보조 모니터 없는 노트북이다.
PC 카카오톡과 Chrome 두 창만 OBS 창 캡처한다.
카카오톡과 Chrome은 사람이 직접 조작한다.

지금은 실행 전 검토만 진행한다.
코드 수정, DB 실행, 예약 생성, 사진 전송, 촬영, 렌더링은 하지 않는다.

확인:
1. 운영체제·OBS·Node.js·Remotion 환경
2. 역할 유지에 필요한 배포·DB 조건
3. 카카오 메뉴 갱신용 정확한 버튼
4. 예약 현황 조회 기간과 촬영 날짜
5. 변경 승인 페이지의 실제 권한 방식
6. 담당 배정과 담당 달력 표시 조건
7. 홍보 초안의 비공개 동작
8. risk 단계 중복 실행 위험
9. 두 창 캡처와 파일 선택창·새 창 처리
10. Remotion 라이선스 적용 조건

규칙:
- 기존 서비스 코드를 변경하지 않는다.
- 비밀번호 파일을 열거나 읽지 않는다.
- 다른 마을 예약·실제 고객 데이터를 열지 않는다.
- SQL은 검토만 하고 승인 없이 실행하지 않는다.
- 확인하지 않은 UI·권한·동작을 추정하지 않는다.
- 문서상 가능과 실제 실행 성공을 구분한다.

결과:
- 코드로 확인
- 실제 실행으로 확인
- 사용자 확인 필요
- 미검증
- 수정 제안

보고 후 승인을 기다린다.

프롬프트 2 — 단일 모니터 촬영 준비

문서의 단일 모니터 운영 기준으로 촬영 준비안을 정리해줘.

범위:
- 카카오톡과 실제 연결된 Chrome의 OBS 창 캡처
- OBS 녹화 시작·종료 단축키 검토
- 10~20초 시험 녹화 체크리스트
- 클립 A~F별 짧은 큐시트
- 각 클립의 시작 화면·risk·성공 확인·중단 조건

제외:
- 한 줄마다 터미널 Enter로 진행하는 방식
- 자동 큐시트 실행기 구현
- 카카오톡 자동 조작
- Chrome 자동 조작
- 기존 서비스 변경

창 캡처의 가림·팝업·최소화 동작은 실제 테스트 항목으로 둔다.
단축키가 안 될 때 OBS에서 직접 시작·종료하는 대안도 작성한다.
설정 완료라고 추정하지 말고 사용자 확인 항목으로 보고한다.

프롬프트 3 — 클립·자막 편집안

현재 촬영 대본은 유지하고 최종 영상의 클립·자막 편집안을 제안해줘.

장면별 항목:
- 장면 ID와 제목
- 원본 클립 A~F
- 대응 대본 번호
- 보여줄 행동과 결과
- 반드시 남길 화면
- 줄여도 되는 대기·반복 구간
- 자막 초안
- 전체 화면 / 카카오 확대 / 웹 확대
- 역할 표시
- 확인 필요 사항

규칙:
- 녹화 클립과 최종 편집 장면을 구분한다.
- 추가 촬영보다 기존 녹화 활용을 먼저 검토한다.
- 영상 확인 전 타임코드와 확대 좌표는 미정이다.
- 자막은 하단 최대 두 줄이다.
- 조작 설명과 개선 배경을 구분한다.
- 세 사람이 동시에 사용한 것처럼 편집하지 않는다.
- 일정 절차는 사무장 제안 → 체험객 동의 → 사무장 확정이다.
- 현재 로그인 역할과 업무상 행동 주체를 혼동하지 않는다.
- 구현되지 않은 기능·확인되지 않은 효과를 추가하지 않는다.

지금은 코드 작성과 렌더링을 하지 않는다.
편집안을 보고하고 승인을 기다린다.

프롬프트 4 — 원본 영상 확인

녹화 원본과 승인된 편집안을 비교해줘.

원본별 확인:
- 길이·해상도·재생 가능 여부
- 대본 단계 대응
- 예약번호·일시·상태 연결
- 역할 표시와 실제 화면 일치
- 개인정보·비밀번호·다른 채팅 노출
- 사용할 구간과 제외할 구간
- 자막 표시 시점
- 실제 확대 영역

영상을 직접 확인할 수 없다면 확인했다고 보고하지 않는다.
메타데이터만 확인한 경우와 화면까지 확인한 경우를 구분한다.
필요하면 사용자에게 특정 장면 캡처나 시간을 요청한다.

절대 시간과 원본 기준 시간을 혼용하지 않는다.
추가 촬영이 필요하면 이유와 최소 범위를 제안한다.

프롬프트 5 — Remotion 한 구간 제작

승인된 편집안과 실제 원본을 기준으로
Remotion에서 20~30초 구간만 먼저 제작해줘.

순서:
1. 라이선스와 환경 확인
2. 설치된 패키지 버전 확인
3. 공식 문서·Agent Skills 확인
4. 원본 재생 검증
5. 실제 시간·확대 영역 확정
6. 자막과 역할 표시
7. 확대 효과
8. 시험 렌더링

규칙:
- 원본 비율을 유지한다.
- 자막과 역할 표시는 확대되지 않게 한다.
- 자막·시간·역할·확대 정보는 데이터로 분리한다.
- 한글 폰트가 최종 렌더에서 정상인지 확인한다.
- 임의의 클릭 위치나 결과를 만들지 않는다.
- 영상 확인이 불가능하면 필요한 값을 요청한다.
- 기존 웹서비스를 수정하지 않는다.
- 작업 완료와 미검증을 구분한다.

전체 확장은 시험 결과에 대한 사용자 승인 후 진행한다.

프롬프트 6 — 전체 확장·최종 검증

승인된 시험 구간의 스타일을 전체 영상으로 확장해줘.

포함:
- 시작 안내 카드
- 역할 전환 표시
- 같은 예약의 연결
- 사무장 제안·체험객 동의·사무장 확정 구분
- 담당 조회 전용 화면

12. 최종 검증·PDF 출력

12.1 내용 검증

  • 같은 예약번호가 끝까지 이어진다.
  • 일시·상태가 실제 화면과 일치한다.
  • 체험객 변경 동의와 사무장 확정이 구분된다.
  • 역할 표시가 실제 시연과 일치한다.
  • 동시 사용으로 오해할 표현이 없다.
  • 확인되지 않은 전달·효과를 주장하지 않는다.

12.2 영상·보안 검증

  • 카카오 버튼과 웹 제목이 보인다.
  • 자막이 주요 조작 영역을 가리지 않는다.
  • 작은 화면에서도 글씨를 읽을 수 있다.
  • 최종 렌더링의 한글 폰트가 정상이다.
  • 비밀번호·개인 채팅·다른 마을 데이터가 없다.
  • 관광객에게 공개와 갯벌체험 중지를 누르지 않았다.

12.3 PDF 저장

  1. 이 HTML을 브라우저에서 연다.
  2. 상단 인쇄 / PDF 저장 또는 Ctrl + P를 누른다.
  3. 대상을 PDF로 저장으로 선택한다.
  4. A4·세로·기본 배율을 먼저 확인한다.
  5. 필요하면 배경 그래픽을 켜고 머리글·바닥글을 끈다.
  6. 표와 프롬프트의 잘림을 인쇄 미리보기에서 확인한다.
  7. 촬영용은 6~7장에 해당하는 페이지를 골라 출력할 수 있다.

실제 페이지 번호는 브라우저·폰트·인쇄 설정에 따라 달라진다. 인쇄 버튼은 인쇄 창을 열 뿐, PDF를 자동으로 생성하거나 저장하지 않는다.

권장 첫 실행

Cursor 프롬프트 1로 사전 검토 → 단일 모니터 시험 녹화 → 클립 A 촬영 → 한 구간 편집 검증 → 나머지 클립 확장.

이 문서는 작업 계획과 검증 기준이다. 실제 구현·서비스 권한·촬영 결과는 환경에서 확인해야 한다. 비밀번호와 토큰을 이 문서에 추가하지 않는다.
